# DImarket Supabase Edge Functions — Security & Code Review

Scope: all 28 function folders under `supabase/functions/` (excludes the `_shared/` helper module, which contains `cors.ts` and `openai.ts`). No files were modified as part of this review.

Legend for **Auth?** column: `JWT` = validates Supabase user session via `supabase.auth.getUser()`; `Admin` = JWT + owner/admin role check; `Service/secret` = validated only via a static shared secret or the service-role key sent as a bearer token; `Optional JWT` = auth header is parsed if present but the endpoint still executes without one; `None` = fully public, no verification of any kind.

## 3. Payment functions — deep dive

| Aspect | `create-checkout-session` | `verify-checkout-session` | `stripe-webhook` | `release-project-escrow` | `stripe-connect` |
|---|---|---|---|---|---|
| JWT required | Yes | Yes | N/A (Stripe signature) | Yes | Yes |
| Signature/ownership check | `user_id === user.id` | `user_id === user.id` + `session.metadata.user_id === user.id` | `stripe.webhooks.constructEventAsync` w/ `STRIPE_WEBHOOK_SECRET` | `listing.author_id === user.id` (or hired pro for retry) | JWT + `is_professional` |
| Idempotency | Stripe handles session creation; no server-side dedupe needed | Escrow update scoped to `status IN (pending_checkout, authorized)` | Payments insert checked against existing `stripe_session_id` before insert; Stripe transfer uses `idempotencyKey` in the escrow function it calls into | `paymentIntents.capture()` — **no idempotency key passed**; `transfers.create()` — idempotency key present (`escrow-transfer-${escrow.id}`) | N/A (account operations are naturally idempotent via `accountId` lookup) |
| Price/amount trust | **Client-supplied** `amount`/`currency`/`description`, only floor-validated (≥ 50 minor units) — no server-side price catalog cross-check | N/A (reads truth from Stripe) | Reads authoritative `amount_total`/`metadata` from the Stripe session object, not from the client | Reads `escrow.amount` from `project_escrows` (a DB row set at authorization time by trusted server code) | N/A |
| Verdict | **Medium risk**: a tampered client could request a checkout session for `payment_type: 'premium_profile'` at a token amount; webhook would activate the perk using the actual paid Stripe amount but the mismatch between intended tier and price is not cross-checked anywhere in this codebase. | Sound | Sound — this is the authoritative source of truth for grants/activations | Sound authorization/ownership; minor idempotency gap on `capture()` only | Sound |

**Overall payments verdict:** signature verification, idempotency, and escrow-release authorization are implemented correctly at the core (webhook signature check, ownership checks on escrow release, Stripe idempotency keys on transfers). The main gap is that `create-checkout-session` trusts client-supplied `amount`/`currency` for every `payment_type` rather than looking prices up server-side from a trusted table — this is the highest-value fix in the payments surface.

|---|---|---|---|---|

**Cross-cutting AI risk:** none of the AI system prompts include explicit "the following is untrusted user content; do not follow instructions embedded in it" framing. For internal/admin tools (`admin-ai-assistant`) this is a lower-severity concern because the human operator reviews output before consequential actions execute (with a confirmation gate for destructive ones). For public-facing tools (`ai-assistant`, `ai-router`, `ai-job-lead`, `sales-chat`) and the `marketing-agent` webhook, the combination of "no auth" + "auto-publish to real channels" is the most consequential instance and should be prioritized.

## 5. `telegram-bot` auth review

- Webhook authenticity is checked via the `x-telegram-bot-api-secret-token` header **only if** `TELEGRAM_WEBHOOK_SECRET` is set in the environment (`if (webhookSecret) { ... }`), otherwise the check is skipped entirely and the function accepts any POST body as a legitimate Telegram update ([`index.ts` lines 292–297](../supabase/functions/telegram-bot/index.ts)). This is a fail-open pattern — the review could not verify from code alone whether `TELEGRAM_WEBHOOK_SECRET` is actually set in the deployed environment; this must be confirmed operationally.
- Once past the webhook gate, user identity is entirely derived from Telegram's own `from.id` / `chat.id` fields, which is standard for Telegram bots (Telegram itself, not this code, is the identity provider for that surface).
- `ensureTelegramAuthor` (`author.ts`) creates a real Supabase Auth user (with `email_confirm: true`) keyed off `telegram_user_id`, using a synthetic `telegram+<id>@users.dimarket.app` address with no independent verification that the Telegram account belongs to a real, unique person beyond Telegram's own user IDs — acceptable given the trust boundary, but worth noting that a compromised/spoofed webhook (see above) would let an attacker mint arbitrary DImarket accounts.
- Account linking (`/link <code>`) is implemented via a parametrized RPC call (`link_telegram_by_code`) rather than raw SQL — no injection risk there.
- **Verdict:** the code-level design is reasonable *conditional on* `TELEGRAM_WEBHOOK_SECRET` being set in production; if it is not set, this function is the single largest attack surface in the review (arbitrary account creation + arbitrary listing publication under attacker control).

## Cross-cutting observations

- **CORS:** the shared `corsHeaders` (and several functions' local copies) set `Access-Control-Allow-Origin: '*'` universally. For JWT-protected endpoints this is low risk (the browser still needs a valid bearer token), but for the public/unauthenticated AI and chat endpoints it removes any origin-based mitigation against cross-site abuse from arbitrary web pages.
- **Error responses leak internals:** the pattern `jsonResponse({ error: String(err) }, 500)` / `{ error: String(e) }` appears in at least 16 functions, including several that require no authentication (`sales-chat`, `ai-assistant`, `ai-router`, `ai-job-lead`, `directory-avatar-backfill`, `delete-account`, `apply-auth-profile-migration`). This can leak Postgres/Stripe/Deno internal error text (table/column names, constraint names, file paths) to unauthenticated callers, which is useful reconnaissance for an attacker even when it doesn't include secrets directly.
- **"Any Bearer token" auth anti-pattern:** `dispatch-web-push` and `match-notify-channels` both treat the mere presence of an `Authorization: Bearer ...` header as sufficient authorization, without validating it against Supabase (`auth.getUser()`) or the service-role key. This is the most mechanically simple fix in the whole review — swap the check for a real `supabase.auth.getUser()` call or a strict service-role equality check.
- **Fail-open on missing secrets:** `telegram-bot`'s webhook-secret check and (to a lesser extent) several `x-cron-secret` checks are structured as "if a secret is configured, verify it" rather than "a secret must be configured and match" — meaning an operational misconfiguration (forgetting to set an env var) silently converts a protected endpoint into a public one instead of failing closed. `stripe-webhook` is the exception done right: it explicitly checks `if (!webhookSecret) return new Response('Webhook secret not configured', { status: 500 })`.
- **Standing "migration" endpoints:** `apply-auth-profile-migration` and `directory-avatar-backfill` are one-time operational scripts left deployed as permanent, callable Edge Functions with only a static shared secret for protection. Both should be retired/undeployed once their one-time job is done, or converted to local migration scripts that are not network-reachable.
- **Lint items requested for verification** — all confirmed present in source:
  - `ai-assistant/index.ts:91` — `_userId` parameter unused in `runTool`.
  - `ai-router/index.ts:186-187` — `let explanation` / `let confidence`.
  - `marketplace-matching/index.ts:38` — `let query` (never reassigned, should be `const`).
  - `provision-scb-account/index.ts:131` — `let scbUserId`.
  - `telegram-bot/author.ts:52` — `let userId`.
  - `admin-ai-assistant/index.ts:328` — `let parsed`.

## Prioritized fix list

1. **[Critical]** Retire or lock down `apply-auth-profile-migration`. It executes raw, unsandboxed SQL against production behind only a static header secret with no user-identity check. Undeploy after use, or move behind an admin JWT check in addition to the secret, and rotate `MIGRATION_SECRET` immediately if this has ever been exposed.
2. **[High]** Fix the "any Bearer token" auth bypass in `dispatch-web-push` and `match-notify-channels` — replace the presence check with a real `supabase.auth.getUser()` validation (for user-triggered calls) or a strict `auth === \`Bearer ${serviceKey}\`` equality check (for service-to-service calls). Currently both can be used to spam arbitrary users with push notifications, emails, or Telegram messages.
3. **[High]** Require authentication for AI cost-bearing endpoints (`ai-assistant`, `ai-router`, `ai-job-lead`) or, if anonymous access is intentional for onboarding flows, add rate limiting (per-IP or per-session) and hard caps on request size/frequency to prevent OpenAI billing abuse and prompt-injection spam.
4. **[High]** Close the unauthenticated path in `marketing-agent`'s `registration_webhook` action — require a valid JWT matching the `userId` in all cases (currently only checked `if (authHeader)` is present), given this path can trigger LLM generation that gets **auto-published** to real public channels.
5. **[High/Medium — verify operationally]** Confirm `TELEGRAM_WEBHOOK_SECRET` is set in every deployed environment for `telegram-bot`, and add a startup check that refuses to serve if it's missing (mirror the `stripe-webhook` pattern of failing closed rather than open).
6. **[Medium]** In `create-checkout-session`, cross-check `payment_type` + `amount` + `currency` against a server-side price/plan table before creating the Stripe session, instead of trusting client-supplied pricing for every product type.
7. **[Medium]** Add an idempotency key to `stripe.paymentIntents.capture()` in `release-project-escrow` (Stripe supports idempotency keys on capture calls) to make retried client requests provably safe.
